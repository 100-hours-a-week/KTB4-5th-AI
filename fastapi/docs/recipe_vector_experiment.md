# 레시피 pgvector 비교 실험 — 2026-10-23

## 적용 범위

실제 로컬 PostgreSQL 17.11 + pgvector 0.8.7에서 레시피 870건을 비교했다. 가짜 벡터나 모의 DB 결과가 아니다. 운영 DB·FastAPI 추천 API·EC2·RunPod에는 연결하지 않았다. 기본 추천 경로는 정확 재료명 검색 그대로이며, 아래 별칭·벡터 경로는 비교 도구에서만 실행한다.

모델은 [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small), revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`, 384차원이다. 공개 모델을 고정 revision의 safetensors로 CPU에 로드하고 `query:`/`passage:` 접두어 및 L2 정규화를 적용했다. 모델을 직접 학습하지 않았다.

## 구성

- `app/recipes/embeddings.py`: 제목·재료명 임베딩. 선택 의존성을 지연 import하므로 FastAPI 기본 실행에서 모델을 로드하지 않는다.
- `app/recipes/vector_repository.py`: 현재 원천 revision·모델 revision·활성 상태가 일치하는 벡터만 검색한다.
- `app/recipes/retrieval.py`: 명시적 별칭과 재료/제외 조건 재검증, RRF 병합. 의미 유사도만으로 재고나 대체 재료를 확정하지 않는다.
- `database/migrations/021_recipe_embeddings.sql`: 선택 적용용 vector(384) 테이블. 앱이 자동 실행하지 않는다. 이번에는 전용 로컬 임시 DB에만 적용했다.
- `database/benchmark_recipe_retrieval.py`: 전용 localhost:15438/recipe_vector_bench 이외 연결을 거부하는 실험 도구. .env를 읽지 않는다.

문서 벡터는 미리 생성하고, 질의 벡터만 요청 시 생성한다. 임베딩 모델·차원·텍스트 구성 버전·원천 revision을 기록한다. 원문이 바뀌면 기존 벡터는 재생성 전까지 검색에서 제외한다. 현재 규모에서는 exact cosine 검색이며 HNSW/IVFFlat 인덱스는 만들지 않았다. [pgvector 공식 문서](https://github.com/pgvector/pgvector)

별칭에는 계란↔달걀, 소고기↔쇠고기/우육, 돼지고기↔돈육, 무↔무우, 브로콜리↔브로컬리만 포함했다. 우유↔두유, 두부↔순두부는 동의어로 취급하지 않는다. 별칭은 후보 조회에 쓰는 명시적 사전이지 사용자 피드백의 전역 승격이 아니다.

## 실험 조건

- Mac arm64, CPU 모델 스레드 2개. 임시 Docker DB는 localhost에만 공개하고 CPU 2개·메모리 1GiB로 제한했다.
- Docker 이미지 digest: `sha256:ac08538c6f8b9904c33c8224c5e5706dbe760aca29db1d096972b4052c22a75d`.
- 합성 재고 질의 22개 × 반복 3회, 각 구간 66회. 제외 재료와 비식품 입력 등 의도적 차단 사례 포함.
- 정확 일치 / 별칭 일치 / 검증 없는 벡터 top50 / 별칭+벡터 RRF 후 재검증을 비교했다.
- 하이브리드는 보유 비율·부족 재료 감점 정책을 우선하고 RRF를 같은 점수 내 순위에 사용한다. 벡터 점수를 confidence나 재료 확정으로 바꾸지 않는다.
- 모든 재고의 소비기한은 유효하다고 통제했다. 소비기한 정책·양 충족·맛·개인 선호는 이번 실험 대상이 아니다.

조회 시간에는 DB 왕복·스냅샷 역직렬화가 포함되며 정확/별칭 경로에는 규칙 순위 계산도 포함한다. 순수 SQL 처리시간이 아니다. 하이브리드 전체는 별칭 조회·질의 임베딩·벡터 조회·검증/병합을 순차 실행한 값이다. 작은 로컬 표본으로 EC2/RunPod 운영 P95나 동시 부하 성능을 예측하지 않는다.

- 별칭으로 조회 가능한 후보가 증가한 질의: 9/22.
- 예: 계란·대파·당근 후보 283→377건, 무우·소고기 후보 29→99건. 이는 원문 후보 수이며 더 맛있는 추천이 됐다는 평가가 아니다.
- 검증 없는 벡터 top5 전체 110개 중 36개가 이름·별칭 재료 일치/제외 규칙을 위반했다. 의도적인 무재료·제외 사례도 포함하므로 일반 사용자 추천 정확도로 해석하지 않는다.
- 검증 후 하이브리드 반환에서는 같은 규칙 위반 0건.
- 별칭 전체 조회 밖에서 추가로 확인된 유효 벡터 후보 0건. 단, 정답 판정과 최종 게이트에 같은 이름·별칭 규칙을 사용하므로 이 실험은 그 규칙 밖의 의미적 이득을 증명할 수 없다.
- 실제 DB에서 오래된 sourceRevision 벡터 차단, INACTIVE 차단을 확인했다. cosine 결과와 NumPy 정규화 내적의 최대 차이는 약 2.19×10^-7이었다.
- 문서 870건 임베딩 약 5.030초. 확인 실행의 모델 로드 약 10.409초. 최초 다운로드가 포함된 선행 실행 로드는 약 43.551초였다. 요청 지연과 구분한다.
- 확인 실행 프로세스 최대 RSS 약 1,097.67MiB. Docker VM/DB 메모리는 별도이며 합산값이 아니다. 따라서 작은 FastAPI 인스턴스에 임베딩 모델을 자동 추가하는 근거로 쓰지 않는다.

## 판단

현재의 **재료 기반 후보 조회**에는 정확 일치와 검토된 별칭이 우선이다. pgvector는 선택적 실험 상태로 유지하며 필수 요청 경로에 넣지 않는다. 의미상 대체 재료를 자동 허용하지 않는다.

벡터 효과를 추가 판단하려면 사람이 관련도를 평가한 홀드아웃 질의가 필요하다. '간단한 두부 요리' 같은 자연어 의도·조리 조건은 현재 요청 API에 없는 입력이므로 별도 계약과 평가 항목을 설계해야 한다. 평가를 통과한 경우에만 shadow 조회 → 결과 점검 → 제한적 활성화를 진행한다.
