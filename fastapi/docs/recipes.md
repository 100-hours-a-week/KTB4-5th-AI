# 레시피 추천·동기화 구조

현행 정책은 v10이다. 정확한 보유 식재료 하나 이상을 쓰면 주재료가 부족해도 추천하고 NEEDS_SHOPPING과 추가 식재료를 표시한다. 검토된 양념·조미료는 부족 목록에서 제외하되 PANTRY_UNVERIFIED로 분량 미확정을 유지한다. 같은 임박 활용·적합성 단계에서 구매 부담이 최소 후보보다 2종 이내인 후보 중 아직 활용하지 못한 임박 주재료의 대표 후보를 우선 선택한다. 미활용 임박 재료는 최종 반환 목록 기준으로 계산한다. ingredientKey와 검토 사전으로 상품명을 연결하며 제외 조건은 유지한다. 상세 계약은 [추천 정책](recipe_ai_recommendations.md)의 첫 절을 따른다. 아래 이전 정책 설명보다 이 절이 우선한다.

## 역할

백엔드가 소유권을 검증한 확정 재고를 전달하면 캐시를 확인하고, miss일 때 AI PostgreSQL 원천 검색 → 일반 추천·확인 후보 분리 → 미활용 임박 주재료의 승인된 원천 보충 → 임박 주재료·적합성 정렬 → 선택적 Gemma RANK 1회 → 순서 검증을 수행한다. AI 실패·생략에도 기본 추천을 유지하고 RULE_FALLBACK으로 구분한다. 사진 분석 큐나 백엔드 MySQL 재고는 수정하지 않는다. 현행 v7 정책은 [단일 AI 순위 조정 추천](recipe_ai_recommendations.md)을 기준으로 한다. Tavily는 키와 승인된 정확 호스트 목록이 있을 때만 최후 보충 경로로 호출한다.

- `app/recipes/schemas.py`: 재고·원천 스냅샷·단위·정렬 검증
- `app/recipes/service.py`: 소비기한 필터, 제외 재료 필터, 점수·캐시
- `app/recipes/planning.py`, `ai.py`, `ai_contract.py`: 기본 추천·단일 AI 순위 조정·Worker 계약
- `app/recipes/quantities.py`: 원본 인분 기준 필요량·부족량·재고 ID별 가상 잔량
- `app/recipes/suitability.py`: 제목·검토 규칙 기반 역할, 물 정책, 주재료 미보유·같은 계열 확인 판정
- `app/recipes/evaluation.py`: 같은 후보의 기본·AI 순위 사실 지표 비교
- `app/recipes/repository.py`: PostgreSQL 원본 저장 및 변경 이력
- `app/recipes/food_safety.py`: COOKRCP01 검색·보수적 정규화
- `app/recipes/ingredients.py`: 괄호형 분량·구분자·분수·단위 파싱
- `app/routers/recipes.py`: 인증된 내부 API

## API

두 API 모두 기존 `X-Internal-API-Key`를 사용한다.

- `POST /ai/v1/recipe-recommendations`: 동기 응답, HTTP 200. 기본 limit=10이며 적합 후보가 부족하면 더 적게 반환한다. 전략이 다른 같은 원천 레시피도 한 번만 반환한다. 명시적인 limit은 1~20을 허용한다. 재고 형식·fingerprint 오류 400, 인증 오류 401, DB·원천 의존성 오류 503.
- `GET /ai/v1/recipe-sync/changes`: HTTP 200. 최초 cursor 생략, 기본 limit=100, 범위 1~500. `items`, `nextCursor`, `hasMore` 반환. 잘못된 cursor는 400.

백엔드가 MySQL 부모·재료·단계를 한 트랜잭션으로 반영한 후에만 nextCursor를 저장한다. `(source, sourceRecipeId)`와 `sourceRevision`으로 멱등 처리한다. 변경 이력은 append-only이며 ACTIVE/INACTIVE 스냅샷 모두 전달한다. 일시적으로 검색되지 않았다는 이유로 INACTIVE 처리하지 않는다. 비활성화는 검증된 원천 상태 변경을 repository에 저장할 때만 발생한다.

## 재고 fingerprint 계약 v1

`inventoryFingerprint`는 클라이언트가 임의로 정하는 키가 아니다. 서버가 재계산해 일치 여부를 검증한다.

1. 검증된 inventory를 ingredientId 오름차순으로 정렬한다.
2. 이름은 Unicode NFKC → casefold → 모든 공백 제거. ID·카테고리·보관형태·수량·중량·소비기한은 포함한다. 수량/중량의 null도 포함한다.
3. 모델 전체 필드를 날짜 `YYYY-MM-DD`의 JSON 값으로 만든다. weightValue는 Python float 직렬화 기준이다(예: 300.0).
4. JSON 객체 키 정렬, 공백 없는 구분자, 한글 UTF-8 원문(`ensure_ascii=False`)으로 직렬화 후 SHA-256 소문자 hex.

정확한 참조 함수는 `inventory_fingerprint()`이다. 다른 언어에서는 숫자 표기까지 동일해야 하므로 백엔드와 공통 fixture를 맞춘 후 연동해야 한다. 요청 필드는 위키 AI 1단계의 레시피 계약을 따른다. category는 현재 분석 API의 Category enum을 재사용한다.

## 이전 기준선 — 추천 정책 v1

아래는 과거 규칙 검색 기준선이다. 현행 요청·응답·캐시는 위 링크의 v7을 따른다. 뒤쪽 날짜별 기록도 당시 실험 범위이며 현재 배포 상태를 보증하지 않는다.

- 기본 EXCLUDE_EXPIRED. 서울 날짜 기준 `expirationDate < 오늘`만 제외한다. 당일은 포함한다.
- 레시피 재료명과 재고명은 검토된 별칭·용도 표제를 포함한 비교 키로 비교한다. 원문과 inventoryFingerprint용 문자열 정규화는 유지한다. 의미 검색·동의어 추측·수량 충족 보장은 하지 않는다. 현재 정책은 `recipe_ai_recommendations.md`의 재료 표기 정규화를 따른다.
- 제외 재료는 정규화 후 레시피 재료명에 부분 문자열로 포함돼도 제외한다. 이는 다국어·교차오염을 포함한 알레르기 안전 보증이 아니다.
- 점수 = `max(0, min(1, 임박 점수 + 보유 비율 점수 - 부족 비율 감점))`.
- 임박은 오늘부터 3일 이내. 임박 점수=0.4×사용 임박 재료종/전체 임박 재료종, 보유 점수=0.6×보유 재료종/레시피 재료종, 감점=0.2×부족 재료종/레시피 재료종.
- 가중치는 초기 정책값이지 검증된 품질 지표가 아니다. 이력 없는 다양성 점수는 0이다.
- 캐시는 냉장고·검증된 재고 fingerprint·제외 재료·모드·limit·서울 날짜 기준으로 분리한다. 기본 TTL 300초, 크기는 REFERENCE_CACHE_MAX_SIZE. 외부 동기화/프로세스 간 캐시 공유는 없고 TTL 이내 이전 스냅샷이 반환될 수 있다.

## DB 및 공급자 활성화

새 `020_recipe_storage.sql`을 **별도 검토·적용**해야 한다. 기존 DATABASE_URL의 PostgreSQL에 독립 `recipe_ai` 스키마를 만든다. 앱이 자동 적용하지 않는다. 실행 계정에는 schema/table/identity sequence 권한이 필요하다.

식품안전나라 키가 아직 없으므로 기본적으로 외부 검색은 꺼져 있다. `RECIPE_FOOD_SAFETY_API_KEY`와 `RECIPE_FOOD_SAFETY_STORAGE_APPROVED=true`가 모두 있어야 호출한다. 후자는 원문 저장·재배포 이용 조건을 운영자가 확인했다는 승인이다. 키 자체는 원천 URL에 들어가므로 HTTP URL을 로그에 남기지 않는다.

원천은 최대 3개 재료를 각 20건 검색한다. 요청당 제한 시간 30초, HTTP 요청당 8초, 429/5xx는 1회 재시도, 호출 간 0.3초 간격이다. 타임아웃·인증 오류·잘못된 원천 응답은 503이며 임의 레시피로 대체하지 않는다. 원문 재료 목록을 모두 확실히 분리할 수 없는 레시피는 저장·추천하지 않는다. 이 보수적 파서는 누락률이 높을 수 있어 실제 응답으로 보완해야 한다. 원문 단위는 amountText에 보존하며 확정 불가 단위는 UNKNOWN/null로 유지한다.

요리명과 일치하는 독립 제목 줄, 명시적인 고명·양념·소스 구역 표시만 분리한다. `소금 약간`처럼 재료명은 식별되지만 분량이 수치가 아닌 경우에도 재료 자체는 유지하며 UNKNOWN/null로 표시한다. 해석되지 않은 일반 줄을 임의로 지워 추천 후보로 만드는 것은 금지한다.

TheMealDB와 Tavily 연결은 이번 범위에 포함하지 않는다. 키·이용 조건과 한국어 재료 매핑을 확정한 뒤 기존 설계의 식품안전나라 → TheMealDB → Tavily 순으로 확장한다. 현재 식품안전나라 유효 결과가 없으면 빈 추천이며, 미설정·오류는 503이다.

운영 DB 마이그레이션·실제 원천 검색·백엔드 MySQL 반영까지의 통합 시험은 별도 수행해야 한다. 단위 시험을 실제 검색 정확도 검증으로 간주하지 않는다.

## 개발용 레시피 사전 수집

`database/collect_recipes.py`는 외부 원본을 페이지별로 조회하고 `database/recipe_staging/<UTC 실행시각>/`에 저장한다. `.env`는 명시적으로 fastapi/.env를 읽으며 키와 키가 들어간 요청 URL을 출력하지 않는다. 기본 상한 2,000건·페이지당 100건·페이지 간 0.5초 간격이다. 429·5xx 및 접속 시간 초과만 최대 두 번 재시도한다.

- `raw.jsonl`: RCP_SEQ로 중복 제거한 원본. 검토 대상도 보존한다.
- `validated.jsonl`: 현재 파서와 Recipe 스키마 검증을 통과한 정규화 스냅샷. 정확도 정답 검증이나 추천 적합성 승인을 뜻하지 않는다.
- `needs_review.jsonl`: 변환되지 않은 원천 ID·이름·분류 사유. 해당 ID의 원본을 raw.jsonl에서 확인할 수 있다.
- `summary.json`: 수집 범위·건수·완료/중단 여부·소요시간. 실패한 경우에도 이미 저장한 원본과 요약을 남긴다.

실행 디렉터리는 새로 만들며 기존 데이터를 덮어쓰지 않는다. 수집 파일 전체는 Git에서 제외한다. 스크립트 자체는 재수집 가능한 관리 도구로 배포 소스에 포함한다. 개발용 로컬 준비 파일 수집과 서비스 원문 저장·재배포 승인은 구분한다. 이 도구는 DB 저장, 캐시 활성화, MySQL 동기화, 승인 설정 변경을 수행하지 않는다.

2026-10-23 수집 결과: 원천이 보고한 총 1,156건과 중복 제거 수집 1,156건이 일치했다. 12페이지, 중복 0건, 약 19.903초, 현재 구조 검증 통과 304건, 검토 필요 852건이다. `SOURCE_EXHAUSTED` 상태로 끝났다. 이 수치는 수집·파싱 결과이며 레시피 추천 정확도나 dev 서버 통합 시험 결과가 아니다.

## 재료 파서 v2 및 원본 재처리

`database/reprocess_recipes.py`는 `--input raw.jsonl`을 읽어 새 디렉터리에 준비 데이터를 생성한다. `--baseline validated.jsonl`을 지정하면 기존 통과본의 누락과 재료 변경을 요약한다. 외부 API를 다시 호출하지 않고, 원본과 이전 실행 결과를 덮어쓰지 않으며 DB에도 쓰지 않는다.

- `돼지고기(50g)`와 `닭고기(가슴살, 120g)`의 분량·부위 설명을 분리한다.
- `배 80g(1/2개)`에서는 주 분량 80g을 유지한다. 괄호의 환산 예시를 주 분량으로 오인하지 않는다.
- 정수·소수·분수·혼합 분수를 읽되 분수 개수와 큰술·컵·알·장 등은 기존 ERD의 정수 EA/g/ml로 임의 환산하지 않는다. UNKNOWN/null과 원문 amountText를 유지한다.
- 괄호 깊이를 추적하여 괄호 바깥 쉼표·줄바꿈만 분리한다. 쉼표 뒤 줄바꿈으로 생긴 빈 조각은 무시하되 비어 있지 않은 미해석 조각은 버리지 않는다.
- 음수·0·0 분모·닫히지 않은 괄호·구분자 없는 복수 분량은 검토 대상으로 둔다.
- `빠금장소스 빠금장(40g)`처럼 구역 제목과 재료명 경계가 불분명한 조각도 통과시키지 않는다. 통과 건수를 늘리기 위해 표제나 재료를 추측 삭제하지 않는다.

추가 통과는 488건이다. 기존 304건의 탈락 0건, 기존 재료 스냅샷 변경 0건이다. 새 통과본의 표본을 원문 분량과 비교하면서 구역 제목이 재료명에 섞이는 사례를 추가 차단했다. 전체 792건의 의미 정확도를 정답 라벨로 검증한 결과는 아니다. baseServings와 의미상 동의어는 여전히 추정하지 않는다. parser 계약 버전이 food-safety-v2로 바뀌므로 동일 재료라도 sourceRevision은 v1과 달라질 수 있다.

원본의 SHA-256은 재처리 전후 일치하며 키·연결 정보·준비 데이터는 Git에 포함하지 않는다. 신규 API 추가·dev 서버 배포·DB 반영은 수행하지 않았다.

## 재료 파서 v3 및 공급자 확장 조사

최신 준비 파일은 `database/recipe_staging/20261023T045355809983Z-food-safety-v3/`이다. v2 대비 검증 통과 792→870건, 검토 대상 364→286건으로 바뀌었다. 추가 78건이며 기존 792건의 탈락·재료 스냅샷 변경은 없다. 원본 1,156건의 SHA-256도 유지된다.

v3는 명시적 같은 줄 `- 양념장 :` 경계, 공백 양쪽이 각각 완전한 재료·분량인 쉼표 누락, `후추약간`/`후추(약간)`을 처리한다. `물녹말(녹말가루 10g, 물 10g)`과 `소금물(물 100g, 소금 3g)`은 원문에 명시된 구성 요소로만 분리한다. 추측한 재료를 추가하지 않는다. 분량 없는 표고버섯 기둥·파마산치즈·도토리묵·올방개묵은 명시적 이름 사전으로 UNKNOWN/null을 유지한다.

mg→g, cc→ml는 단위 환산만 수행한다. 원문 `우유 180mg`를 흔한 분량으로 보정해 ml로 바꾸지 않는다. 물의 g도 임의로 ml로 바꾸지 않는다. 표본 비교에서 드러난 `1인분 봄동` 같은 메타데이터 혼합 이름은 차단한다. 명시적 구분 없이 붙은 요리 제목과 재료는 여전히 검토 대상으로 둔다. 문법 파싱이 재료명의 의미 정확도를 보증하지는 않는다.

이전 절의 '공백으로 이어진 복수 분량은 모두 제외' 정책은 v3에서 전체 조각을 완전히 해석할 수 있을 때만 분리하도록 좁혀졌다. 괄호 누락·이름 없는 분량·해석되지 않은 잔여 문구는 계속 제외한다. 870건 전체의 정답 기반 의미 정확도나 dev 통합 시험을 완료한 것은 아니다.

신규 공급자 조사와 실제 샘플 조회 범위, 라이선스 확인이 필요한 부분은 [레시피 원천 확장 조사](recipe_sources.md)에 정리했다. 외부 API 추가 활성화·배포·DB 반영·커밋은 수행하지 않았다.

## 선택적 벡터 검색 실험

현재 API는 벡터 검색을 호출하지 않는다. 870건에 실제 pgvector·다국어 임베딩을 적용한 비교 결과와 적용을 보류한 이유는 [벡터 검색 실험](recipe_vector_experiment.md)에 정리했다. `retrieval` 선택 의존성을 설치하는 것만으로 모델이 시작되거나 DB가 변경되지 않는다.

## 별칭 검색 적용 및 통합 검증 — 2026-10-23

초기 추천 코드에는 달걀/계란, 쇠고기/소고기, 우육/소고기, 돈육/돼지고기, 무우/무, 브로컬리/브로콜리 별칭을 적용했다. 이후 `recipe-ingredient-v2`에서 양송이/양송이버섯 등 검토된 표기와 원문 용도 표제의 비교 키를 보강했다. 현재 목록과 상태 보존 경계는 `recipe_ai_recommendations.md`의 재료 표기 정규화를 따른다. 원천 재료명·분량·sourceRevision과 요청 inventoryFingerprint 계약은 바꾸지 않는다. 점수와 임박 재료 매칭에도 같은 정규화를 사용하며, 캐시 키에는 재료 매칭 버전을 포함한다.

제외 재료는 별칭을 확장해 복합 이름에도 검사한다. 예를 들어 계란 제외 시 달걀노른자도 제외한다. 제외되거나 기한이 지난 재고는 후보 질의에서 제거하며 사용할 재고가 없으면 외부 호출 없이 빈 추천을 반환한다. 의미상 대체 재료를 자동 허용하는 정책은 아니다.

임시 로컬 PostgreSQL에 실제 준비 데이터 870건을 저장하고 HTTP API 6개 요청을 검증했다. 계란/달걀과 소고기/쇠고기는 각각 동일한 상위 5개 원천 ID를 반환했다. 우유만 보유하면서 우유를 제외한 요청은 200과 빈 배열, 두부 보유·계란 제외 요청은 200과 5개 후보를 반환했다. 원격 GPU 호출은 없었으며 임시 DB는 시험 후 종료했다. 운영 DB·dev 서버 배포 검증과 구분한다.

## Tavily 원천 발견 도구

`app/recipes/tavily.py`와 `database/discover_recipe_sources.py`는 TAVILY_API_KEY(RECIPE_TAVILY_API_KEY도 허용)로 기본 검색을 수행한다. 검색 결과는 제목·공개 URL·검색 점수만 보존하며 PENDING_SOURCE_AND_USAGE_REVIEW로 표시한다. 본문·이미지를 가져오거나 Recipe를 생성·저장하지 않는다. 검색 점수는 추천 정확도가 아니다.

기본 요청은 basic, 자동 검색 깊이 변경·답변 생성·원문 포함을 끄며 호출 시도는 1회다. 시간 제한, 응답 크기 제한, 호출 간격과 안전한 오류 처리를 적용했다. 명시적으로 시도를 2회로 설정한 경우에만 429를 한 번 재시도한다. 키·인증 헤더·외부 오류 원문은 로그에 기록하지 않는다.

실제 기본 검색 1회는 약 4.362초에 후보 5건을 반환했다. 레시피 반입은 0건이다. 현재 추천 요청에 Tavily 자동 폴백을 연결하지는 않았다. 원문 이용 권한과 재료·조리 단계 검증 없이 검색 결과를 정상 레시피로 바꾸지 않으며, TheMealDB도 아직 미연동이다. 이번 변경은 로컬 코드와 검증 결과이며 커밋·배포·운영 DB 변경을 수행하지 않았다.
