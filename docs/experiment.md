## 2026-09-21 (2) — product_knowledge 공개 데이터셋 대량 시딩 (238,800건)

지난 실험(아래)에서 상품 카탈로그를 하나씩 손으로 채우던 걸(003/005, 34건), 공개 데이터셋으로 대량 확장했다.

**데이터 출처**: 식품안전나라 K-FIND 가공식품 DB(https://various.foodsafetykorea.go.kr/nutrient/). 로그인/회원가입 없이 간단한 "활용정보 입력" 설문(소속·기관유형·활용목적)만 작성하면 받을 수 있음을 확인. 31만여 행, 약 200MB 엑셀.

**처리 과정**:
- openpyxl로 파싱 시도 → 2분 넘게 CPU 100%로 안 끝나서 중단, `python-calamine`(Rust 기반)으로 교체 → 25초 만에 전체 로드
- 식품대분류명(+ "절임류 또는 조림류"는 중분류까지)으로 우리 Category enum에 매핑. 한 갈래로 확신 못 하는 대분류(농산가공식품류·조림류·특수영양식품 등, 전체의 12.6%)는 근거 없이 추측하지 않고 제외
- `normalize_product_name()`(기존 앱 함수 재사용)으로 정제 + 정규화명 기준 중복 제거 → 최종 238,817건
- 사용자 확인: 전체 규모 그대로 진행할지 신뢰도 높은 카테고리만 우선 넣을지 물어봄 → "전체 그대로 진행" 선택
- EC2 배포 중 실제 이슈 발견·해결: `\copy`는 psql 클라이언트 실행 유저 기준으로 파일을 읽는데, `sudo -u postgres`로 실행하면 `postgres` 유저가 `ec2-user` 홈 디렉터리(700 권한)에 못 들어감 → `/tmp`에 같은 상대경로 구조로 복사해서 해결
- 마이그레이션 006 적용: `COPY 238817` → `INSERT 0 238800`(기존 003/005의 34건과 겹친 17건은 `ON CONFLICT DO NOTHING`으로 자동 스킵)

**검증 결과 (영수증2.jpg)**: 기존 4개 → **6개**로 늘어남. 이전엔 유사도 임계값(0.4) 미달로 미해결이었던 "챗잎"(→Gemma가 가격힌트로 해결)과 "브로커리"가 이제 대량 데이터 안의 후보와 매칭돼 해결됨.

**실제로 관찰한 트레이드오프**: "브로커리"(OCR 오타, 의도는 "브로콜리")가 대량 데이터셋의 실제 상품 "브로커리팩"과 유사도 0.57로 더 가깝게 매칭돼 카테고리가 VEGETABLE 대신 PROCESSED로 나옴 — 데이터가 많아질수록 우연한 문자열 유사도 충돌 위험이 커진다는 걸 실제로 확인. `CATALOG_FUZZY` 소스로 구분 표시되고 `NEEDS_REVIEW` 상태라 최종 확정 전 사용자 확인을 거치므로 심각하지는 않지만, 알려진 한계로 문서화(`database/README.md`).

## 2026-09-21 — OCR 속도 최적화 & Gemma 분류 정확도 개선 (GS25 영수증 리콜 0/3 → 3/3)

### 1. OCR 속도 최적화

목표: OCR이 전체 처리 시간의 ~80%를 차지해서 이걸 줄이는 게 최우선이었음.

| 테스트한 것 | 결과 | 채택 여부 |
|---|---|---|
| `PP-OCRv5_mobile_det`(경량 detection 모델)로 교체 | 28% 빨라지지만 핵심 상품명이 통째로 사라지고 한자 섞인 깨진 텍스트 발생 | **기각** |
| `text_det_limit_side_len`(입력 해상도 제한) 축소 | 실행마다 결과가 들쭉날쭉해 신뢰 불가 | **기각** |
| `use_textline_orientation=False`(텍스트줄 방향 분류 끄기) | 실영수증 3장에서 식품/상품 줄 손실 없이 5~28% 빨라짐 | **채택** (기본값) |
| `PADDLE_HPI_BACKEND=onnxruntime`(고성능 추론) | `enable_hpi=True` 전체 자동 선택은 MKLDNN과 동일한 oneDNN/PIR 크래시 발생 → text_detection·text_recognition **두 모델만** ONNX Runtime으로 강제, 나머지는 HPI 안전 자동설정에 맡김 → 크래시 없이 추가 8~48% 개선 | **채택** (옵션) |

**결과**: GS25 기준 OCR 19.2초 → 8~13초대로 단축.

**리뷰 중 발견한 버그**: HPI 의존성이 없는 환경으로 재배포되면 OCR 전체가 죽는 구조였음 → 실패 시 표준 경로로 자동 폴백하도록 수정. 존재하지 않는 백엔드 값으로 강제 실패시켜 폴백이 실제 작동하는지 검증함.

### 2. Gemma 분류 정확도 — 여러 번 실패하다 결국 성공

GS25 영수증의 "마운틴틀러스트"라는 낯선 브랜드명을 Gemma가 계속 놓치는 문제를 붙잡고 여러 라운드에 걸쳐 테스트함.

**실패한 시도들** (전부 직접 curl로 격리 테스트):
- "애매하면 포함하라"는 완화된 프롬프트 → 실패
- 편의점 맥락 주입("GS25에서 파는 흔한 상품은...") → 실패
- `think:true` 추론 모드 → 실패, 게다가 57초나 걸려 운영 불가
- 시스템 프롬프트 단축(JSON 스키마가 어차피 형식을 강제하니 중복 설명 제거) → 오히려 다른 정상 케이스(우유→DAIRY, 애호박→VEGETABLE) 오분류 유발, 폐기
- 자유 응답(형식 제약 없이) 테스트 → 모델이 스스로 "정보가 없다"고 답함, **진짜 지식 부족**임을 확인

**결정적 전환점**: GS25 좌표를 다시 보니 상품명·수량·가격이 실제로는 깔끔하게 정렬돼 있었는데, 상품번호(001/002...)가 없어서 기존 행 복원 로직이 통째로 실패하고 있었음.

### 3. 핵심 파싱 로직 확장 (진짜 버그 발견·수정)

- 번호 없는 영수증(GS25형)용 대체 앵커 탐지(`_name_anchors`) 추가 — 같은 행에 수량+금액이 **둘 다** 있는 줄만 상품행으로 인정
- **1차 구현은 합성 테스트만 통과하고 실제 이미지에선 실패** — 원인: 헤더가 없는 영수증에서 열 위치가 전역 비율 기본값(63/76/91%)으로 잘못 추정됨
- 실제 숫자 토큰 위치로 열을 직접 추정(`_empirical_column_centers`)하도록 수정 → 실제 이미지로 재검증해서 성공 확인
- **효과**: GS25 분류 대상 22줄 → 3줄(진짜 상품행), Gemma 미해결 줄 20줄 → 1줄

### 4. 최종 결론 — 가격 힌트

행 복원이 성공하면서 확보된 수량·가격 정보를 Gemma 프롬프트에 힌트로 붙이는 실험(`"마운틴틀러스트 (수량 1개, 2,100원)"`)을 했더니:
- 격리 테스트: 힌트 있으면 인식, 없으면 여전히 제외 → 정확히 원하는 동작
- 다른 보일러플레이트 줄에 실수로 붙지 않는지 회귀 확인 → 안전
- **실제 API로 최종 검증**: GS25 리콜 **0/3 → 3/3** 완성

| 상품 | 최종 결과 |
|---|---|
| 마늘빅프랑크 | CATALOG (DB 정확 일치) |

| 마운틴틀러스트 | MODEL_INFERENCE (Gemma + 가격 힌트) |
